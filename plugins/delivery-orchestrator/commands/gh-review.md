# /gh:review

An adversarial review board. The point is not to produce *more* review comments —
it is to produce only the ones that are actually true.

## Usage

```
/gh:review 482                     # review PR #482, report findings
/gh:review 482 --comment           # post surviving findings as inline PR comments
/gh:review 482 --fix               # apply surviving findings to the working tree
/gh:review --branch                # review the current branch diff, no PR needed
/gh:review 482 --lens security,tests
/gh:review 482 --quorum 3          # require 3 of 3 skeptics to fail to refute
```

## The protocol

### Stage 1 — Parallel lenses

Six agents review the same diff simultaneously, each blind to the others. Each
lens has a narrow mandate so it does not dilute into generic commentary:

| Lens | Agent | Mandate |
| --- | --- | --- |
| Correctness | [`correctness-reviewer`](../agents/correctness-reviewer.md) | Logic errors, null/undefined paths, off-by-one, race conditions, error handling |
| Security | [`security-reviewer`](../agents/security-reviewer.md) | Injection, authz gaps, secret exposure, unsafe deserialization, SSRF |
| Tests | [`test-coverage-critic`](../agents/test-coverage-critic.md) | Untested branches, assertions that cannot fail, missing regression test |
| API contract | [`api-contract-reviewer`](../agents/api-contract-reviewer.md) | Breaking changes, schema drift, versioning, backward compatibility |
| Performance | [`performance-reviewer`](../agents/performance-reviewer.md) | N+1 queries, unbounded loops, allocation in hot paths, missing indexes |
| Docs | [`docs-reviewer`](../agents/docs-reviewer.md) | Stale docs, undocumented breaking changes, missing changelog entry |

### Stage 2 — Adversarial verification

Every finding is handed to independent [`adversarial-verifier`](../agents/adversarial-verifier.md)
instances, each **prompted to refute it**, not to confirm it. A verifier must
produce a concrete counter-example or a code path that shows the finding is
wrong. The default is `refuted = true` when uncertain.

A finding survives only if it fails to be refuted by the configured quorum
(default 2 of 3).

This stage is why the board is worth running. A single reviewer that "notices" a
null-pointer risk is often reading the code wrong; a skeptic asked to *prove it
cannot happen* finds the guard clause three lines up.

### Stage 3 — Synthesis

[`review-synthesizer`](../agents/review-synthesizer.md) merges surviving
findings on a blackboard, deduplicates across lenses (two lenses often find the
same defect from different angles), ranks by severity, and emits a single verdict.

## Verdict

```
VERDICT: REQUEST_CHANGES   (2 blocking, 3 non-blocking)

BLOCK  src/api/user.ts:114
  `user.id` dereferenced before the `!user` guard on line 121.
  Fails when: GET /users/:id with an id that has no row → 500 instead of 404.
  Survived: 3/3 verifiers could not refute.

BLOCK  src/billing/charge.ts:58
  Retry loop has no maximum; a persistent 402 from Stripe spins forever.
  Fails when: card declined permanently → unbounded retry, budget burn.
  Survived: 2/3 verifiers.

SUGGEST src/api/user.ts:87
  `findMany` inside the map is an N+1 — 1 + N queries for N users.

DROPPED (refuted, not reported): 5 findings
  - "missing await on line 42" → refuted: the function is sync, verified at src/util/id.ts:9
  - …
```

Severity maps to review action: any `BLOCK` → `REQUEST_CHANGES`; only
`SUGGEST`/`PRAISE` → `APPROVE` with comments.

## Flags

| Flag | Effect |
| --- | --- |
| `--comment` | Post surviving findings as inline PR review comments (one pending review, submitted once) |
| `--fix` | Apply surviving findings to the working tree, then re-run the affected lens |
| `--lens <list>` | Restrict to named lenses |
| `--quorum <n>` | Verifiers that must fail to refute for a finding to survive (default 2 of 3) |
| `--no-verify` | Skip stage 2. Faster, noisier, not recommended |
| `--effort <level>` | `low`/`medium` → fewer, high-confidence findings; `high`/`max` → broader sweep |

## Posting rules

When `--comment` is used, comments are posted as **one** pending review
submitted once — never as a stream of individual comments. Every posted body
ends with the attribution footer:

```

---
_Generated by [Claude Code](https://claude.ai/code)_
```
