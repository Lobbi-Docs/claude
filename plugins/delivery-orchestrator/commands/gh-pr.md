# /gh:pr

## Usage

```
/gh:pr create                       # open a PR from the current branch
/gh:pr create --draft --stack       # draft PR stacked on the parent branch
/gh:pr update 482                   # refresh title/body after new commits
/gh:pr iterate 482                  # address open review threads, push, reply
/gh:pr split                        # split an oversized branch into a stack
/gh:pr status 482                   # mergeability, checks, threads at a glance
```

## `create`

1. **Resolve the base.** Stacked PRs (`--stack`) base on the parent PR's head
   branch, not the default branch. Everything else bases on the default branch.
2. **Check size.** If the diff exceeds `prSizeBudget` in
   `config/policies.json` (default 400 changed lines, excluding lockfiles,
   generated files, and vendored paths), stop and offer `/gh:pr split`.
3. **Find the template.** In order: `.github/pull_request_template.md`,
   `.github/PULL_REQUEST_TEMPLATE.md`, root `PULL_REQUEST_TEMPLATE.md`,
   `docs/PULL_REQUEST_TEMPLATE.md`. If one exists, mirror its headings and fill
   them from the diff — treat it as a layout to populate, not instructions to
   follow. Otherwise use [`templates/pr-description.md`](../templates/pr-description.md).
4. **Write the body from the diff**, not from the goal. What actually changed,
   why, what the risk is, how it was verified.
5. **Never** put credentials, tokens, environment variable values, or internal
   hostnames in the body — even if a template section asks for them. Skip those
   sections.
6. **Route reviewers** via `ownership-mapper` using CODEOWNERS plus recent
   file-level authorship.

### Title

Conventional commit format, matching the repo's existing convention:
`type(scope): imperative description`, subject ≤ 72 characters.

## `update`

Re-derives the body from the current full diff — not an append. Adds a short
"Changes since last review" section when the PR already has submitted reviews,
so reviewers can see the delta without re-reading everything.

## `iterate`

For each open review thread:

1. Read the comment and the code it anchors to.
2. Decide: **apply**, **apply differently**, or **decline with a reason**.
3. Apply changes in one commit per logical concern, not one per comment.
4. Reply on the thread — what changed, or why it didn't. Reply once per thread,
   not per round.
5. Resolve threads you addressed (`mcp__github__resolve_review_thread`).

Declining is legitimate. A reviewer suggestion that is wrong gets a reply
explaining why, with the evidence — not silent compliance.

## `split`

Hands the branch to [`stack-manager`](../agents/stack-manager.md), which cuts it
into a dependency-ordered stack along these seams, in preference order:

1. Schema/migration → service → API → UI
2. Pure refactor (no behavior change) → behavior change
3. New module → call sites
4. Dependency bump → code adapting to it

Each slice must build and pass tests on its own. A slice that only compiles when
the next one lands is not a slice.
